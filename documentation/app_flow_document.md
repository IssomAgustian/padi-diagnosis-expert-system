# App Flow Document for Padi Diagnosis Expert System

## Onboarding and Sign-In/Sign-Up
A new user begins by visiting the public landing page, which clearly displays the product name, a brief introduction to the expert system, and a prominent button labeled “Sign in with Google.” When the user clicks this button, they are redirected to Google’s OAuth consent screen. Once they grant permission, the application receives an authentication token from the Flask backend and stores a session cookie in the browser. The user is then automatically redirected to the dashboard. If a user attempts to access a protected page without being signed in, the system immediately takes them to the landing page and prompts them to sign in. In the header of every authenticated page, there is a user avatar or email display that, when clicked, reveals a menu with a “Sign Out” option. Clicking “Sign Out” clears the session cookie and returns the user to the landing page. Because authentication is handled exclusively via Google OAuth in this version, there is no email/password signup or password recovery flow.

## Main Dashboard or Home Page
After successfully signing in, the user lands on the dashboard at the path `/dashboard`. At the top is a fixed header showing the application logo on the left and the user avatar on the right. Along the left side is a vertical menu containing links to the “Diagnosis” page, the “History” page, and the “Settings” page, as well as a “Sign Out” link at the bottom. The main content area displays a welcome message personalized with the user’s name and a brief explanation of the system’s purpose. A large button labeled “Start Diagnosis” sits in the center of the content area to guide first-time users, while returning users can click the “Diagnosis” link in the sidebar. The layout remains consistent as the user moves to other sections, with the sidebar and header always visible.

## Detailed Feature Flows and Page Transitions

### Diagnosis Flow
When the user clicks the “Diagnosis” link in the sidebar or the “Start Diagnosis” button on the dashboard, they are taken to `/dashboard/diagnosis`. The page displays a searchable list of rice plant symptoms loaded from the Flask API. Each symptom can be toggled on or off, and the user may select any number of symptoms. Below the symptom list is a button labeled “Diagnose.” If the user clicks “Diagnose” without selecting any symptoms, a red banner appears at the top of the symptom list indicating that at least one symptom must be selected. Otherwise, the system sends a POST request to the endpoint `/api/diagnose` on the Flask server.

### Conditional Certainty Factor Flow
If the backend finds a rule that fully matches the selected symptoms, it responds with a complete diagnosis and a treatment plan enriched by generative AI. In that case, the page immediately transitions to display the diagnosis result. If the backend determines that the symptoms do not yield a clear rule match, it returns a status indicating that certainty factor input is required. The same page then dynamically replaces the symptom list with a set of sliders or numeric inputs next to each selected symptom. A new button labeled “Submit Certainty Factors” appears. When the user adjusts each slider to reflect their confidence (from 0 to 1) and submits, a POST request is sent to `/api/calculate_certainty`. The backend performs the certainty factor calculation and returns the final diagnosis, which is then rendered on the page.

### Result Display and Print-to-PDF Option
Once a complete diagnosis is available, the page shows a result card containing the disease name, the AI-generated treatment steps, and recommended medicines. Below the result, there are two buttons: “Print to PDF” and “Diagnose Again.” Clicking “Print to PDF” invokes a client-side print library that generates a formatted PDF of the diagnosis card. Clicking “Diagnose Again” resets the page to the initial symptom selection view so the user can perform a new diagnosis. The result is automatically saved to the user’s history on the backend.

### History Page Flow
When the user clicks “History” in the sidebar, they are taken to `/dashboard/history`. This page fetches the last 30 days of diagnoses for the signed-in user from `/api/history` on the Flask backend. The diagnoses appear in a paginated table showing the date, diagnosed disease, and a brief summary of certainty factor scores if applicable. The user can click on any row to expand that record and view full details, including the symptoms, certainty factor values, and treatment plan. Within each expanded entry is a “Print to PDF” button that functions identically to the one on the diagnosis result page. Pagination controls appear at the bottom to allow viewing earlier results in blocks of ten.

### Admin Panel (Advanced Workflow)
If the logged-in user has an admin role, an extra link labeled “Admin Panel” appears above the “Settings” link in the sidebar. Clicking it navigates to `/dashboard/admin` where global diagnostic history for all users can be viewed. Similar pagination and expand-to-detail interactions are present. The admin can filter records by user email or date range and can export a CSV of the selected data. The design of the panel mirrors the user history page but includes additional controls for filtering and data export.

## Settings and Account Management
The “Settings” link in the sidebar leads to `/dashboard/settings` where the user can manage their account information. The page displays their name and email address in editable fields. Below that, there is a toggle for receiving email notifications about new features or system updates. Changes are saved by clicking a “Save Changes” button at the bottom, which sends a PATCH request to `/api/user` on the backend. A confirmation message appears briefly on success. To return to the main flow, the user can click any link in the sidebar or the application logo in the header to go back to the dashboard.

## Error States and Alternate Paths
If a user’s session expires or they manually clear cookies, any attempt to access `/dashboard` or its child routes redirects them back to the landing page with a message asking them to sign in again. Should the app lose network connectivity during a request, a banner appears at the top of the page stating that the application is offline and will retry automatically when connectivity is restored. If the backend returns an error for any API request—for example, due to malformed data or server issues—the page displays an error message and offers a “Retry” button. For restricted admin pages, if a non-admin user attempts to navigate to `/dashboard/admin` directly, they are redirected to the dashboard and shown a notice that they do not have permission to access that section.

## Conclusion and Overall App Journey
From discovering the landing page to signing in with Google OAuth, the user is guided through a clear and consistent interface. The protected dashboard surface gives access to the core expert system functions: selecting symptoms, optionally providing certainty factors, and viewing AI-driven treatment recommendations. The user can review past diagnoses in a history view, export results, or print professional PDF reports. Admin users gain additional oversight through a dedicated panel. Throughout the application, error states are handled gracefully, and user preferences can be updated in settings. This flow ensures that both casual and power users can complete their diagnostic tasks quickly and reliably, all while maintaining a seamless daily experience.
